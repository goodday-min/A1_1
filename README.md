# 📝 나만의 프롬프트 관리 프로그램 (Prompt Manager)

터미널에서 메뉴 번호를 입력해 프롬프트를 추가·조회·검색·즐겨찾기 관리할 수 있는 파이썬 콘솔 프로그램입니다.  
자주 쓰는 AI 프롬프트를 카테고리별로 정리하고, 필요할 때 빠르게 찾아볼 수 있도록 만들었습니다.

---

## 📌프로그램 소개

- 터미널(콘솔)에서 번호를 입력해 기능을 선택하는 메뉴 기반 CLI 프로그램입니다.
- 실행하는 동안 추가한 프롬프트/즐겨찾기 상태는 유지되며, 종료하면 초기화됩니다.  
  (단, 처음 등록하는 기본 프롬프트 3개는 예외입니다 — 아래 [데이터 저장 정책](#데이터-저장-정책-중요) 참고)

## 📌. GitHub 저장소 만들고 로컬과 연결하기

### ✅. GitHub에 새 저장소 생성

1. [github.com](https://github.com) 로그인 → 우측 상단 **+ → New repository**.
2. Repository name 입력 (예: `A1_1`).
3. Public/Private 선택 → **Create repository** 클릭.
   (README, .gitignore는 로컬에서 직접 만들 것이므로 자동 생성 체크는 하지 않아도 됩니다)
4. 생성된 저장소의 **HTTPS URL**을 복사해 둠.
   예: `https://github.com/goodday-min/A1_1.git`

### ✅. GITHUB 저장소 clone 

```bash
git clone https://github.com/goodday-min/A1_1.git
```

### ✅. 프로젝트 폴더 생성 및 로컬 저장소 초기화

```bash
mkdir A1_1
git init
```

- `git init` : 현재 폴더를 Git이 관리하는 저장소로 만듬. (숨김 폴더 `.git` 생성)

### ✅. 파일 준비

- 이 저장소에 있는 `A1_1.py`, `README.md`, `.gitignore` 파일을 `A1_1` 폴더 안에 복사해 넣는다.

### ✅. 원격 저장소 연결 및 첫 커밋/푸시

```bash
git remote add origin https://github.com/A1_1/A1_1.git

git add .
git commit -m "chore: 프로젝트 초기화 및 .gitignore, README 추가"

git push -u origin main
```

- `git remote add origin <URL>` : 로컬 저장소와 GitHub 저장소를 연결합니다.
- `git add .` : 변경된 파일을 커밋 대상(스테이징 영역)에 올립니다.
- `git commit -m "메시지"` : 변경 내용을 하나의 기록(커밋)으로 저장합니다.
- `git push -u origin main` : 로컬 커밋을 GitHub의 `main` 브랜치로 업로드합니다.
  (`-u` 옵션은 이후부터 `git push`만 입력해도 되도록 연결을 기억시켜 줍니다)

  원격 저장소의 최신 내용을 내려받을 때는 `pull`을 사용합니다. 

```bash
git pull origin main
```

## 📌. 프로그램 실행 방법

```bash
cd A1_1
python A1_1.py
```

- **최초 실행**이면 "기본 프롬프트 3개를 입력해주세요"라는 안내가 나옵니다.
  제목/내용/카테고리를 순서대로 3번 입력하면 `prompts.json` 파일에 저장됩니다.
- 이후 화면에 출력되는 메뉴에서 원하는 기능의 번호를 입력합니다.
- `0`을 입력하면 프로그램이 종료됩니다.

## ✅ 기능 목록

| 번호 | 기능 | 설명 |
|---|---|---|
| 1 | 프롬프트 추가 | 제목/내용/카테고리를 입력해 새 프롬프트를 등록합니다. 빈 값은 재입력을 요청합니다. |
| 2 | 프롬프트 목록 | 저장된 모든 프롬프트를 번호, 제목, 카테고리, 즐겨찾기 여부(⭐)와 함께 출력합니다. |
| 3 | 카테고리별 조회 | 카테고리를 선택하면 해당 카테고리의 프롬프트만 모아서 보여줍니다. |
| 4 | 프롬프트 검색 | 키워드를 입력하면 **제목 또는 내용**에 포함된 프롬프트를 검색합니다. |
| 5 | 프롬프트 상세 보기 | 번호를 입력하면 제목, 카테고리, 즐겨찾기 여부, 전체 내용을 보여줍니다. |
| 6 | 즐겨찾기 추가/해제 | 번호를 입력해 즐겨찾기 상태를 켜고 끌 수 있습니다. |
| 7 | 즐겨찾기 목록 | 즐겨찾기로 등록한 프롬프트만 모아서 보여줍니다. |
| 8 | 프롬프트 수정 | 기존 프롬프트의 제목/카테고리/내용을 수정합니다. |
| 9 | 프롬프트 삭제 | 확인 후 프롬프트를 목록에서 삭제합니다. |
| 0 | 종료 | 프로그램을 종료합니다. |

메뉴 번호가 아닌 값을 입력하면 안내 메시지를 출력하고 다시 메뉴로 돌아갑니다.

## ✅ 데이터 저장 정책 (중요)

| 구분 | 대상 | 저장 방식 | 프로그램 종료 시 |
|---|---|---|---|
| **기본 프롬프트** | 최초 실행 시 직접 입력한 3개 | `prompts.json`에 영구 저장 | **유지됨** (다음 실행에도 그대로 불러옴) |
| **임시 프롬프트** | 4번째부터 추가하는 프롬프트 | 메모리(리스트)에만 존재 | **초기화됨** (사라짐) |

- 처음 프로그램을 실행하면 `prompts.json` 파일이 없으므로, 기본 프롬프트 3개를 직접 입력받아 파일로 저장합니다.
  (이전 미션에서 작성한 프롬프트를 입력하면 됩니다)
- 기본 프롬프트 3개는 **수정·삭제도 가능**하며, 수정/삭제하면 `prompts.json`에도 바로 반영됩니다.
- 4번째 이후 추가한 프롬프트는 실행 중에는 자유롭게 추가·수정·삭제할 수 있지만 `prompts.json`에는 저장되지 않으므로,
  프로그램을 다시 실행하면 기본 3개만 남고 나머지는 초기화됩니다.
- `prompts.json`은 사람마다 입력 내용이 달라지는 개인 데이터 파일이라 `.gitignore`에 등록되어 있어 GitHub에는 올라가지 않습니다.

## 등록된 프롬프트 카테고리

프롬프트는 다음 6가지 카테고리 중 하나로 분류하거나, 직접 새 카테고리명을 입력할 수 있습니다.

- **텍스트 생성** – 블로그 글, 카피라이팅 등 텍스트 작성용 프롬프트
- **이미지 생성** – 이미지 생성 AI에 사용하는 프롬프트
- **영상 생성** – 영상 생성 AI에 사용하는 프롬프트
- **페르소나** – 특정 역할/전문가 캐릭터를 부여하는 프롬프트
- **자동화** – 코드 작성, 리뷰 등 업무 자동화용 프롬프트
- **기타** – 위 분류에 속하지 않는 프롬프트

## Git 명령어 한눈에 정리

| 명령어 | 의미 |
|---|---|
| `git init` | 현재 폴더를 Git 저장소로 초기화 |
| `git add <파일>` | 변경 내용을 커밋 대상(스테이징 영역)에 추가 |
| `git commit -m "메시지"` | 스테이징된 변경 내용을 하나의 기록으로 저장 |
| `git push` | 로컬 커밋을 원격 저장소(GitHub)로 업로드 |

## Git이란?

Git은 소스 코드의 변경 이력을 관리하는 **분산 버전 관리 시스템(DVCS, Distributed Version Control System)**이다.
파일이 어떻게 변경되어 왔는지를 시간 순서대로 기록하고, 필요하면 과거 특정 시점으로 되돌리거나 여러 사람이 동시에 작업한 내용을 하나로 합칠 수 있게 해준다.

### Git의 핵심 특징

- **분산 구조**: 중앙 서버(예: GitHub)뿐 아니라 개발자 각자의 로컬 컴퓨터에도 전체 저장소(히스토리 포함)의 복사본이 존재한다. 서버가 다운되어도 로컬에서 작업을 계속할 수 있다.
- **스냅샷 기반 저장**: 파일의 "변경분(diff)"만 저장하는 다른 시스템과 달리, Git은 커밋할 때마다 전체 프로젝트 상태를 스냅샷으로 저장한다. (내부적으로는 중복을 제거해 효율적으로 저장)
- **빠르고 가벼운 브랜치**: 브랜치 생성/전환 비용이 매우 낮아 새로운 기능이나 실험을 부담 없이 시도할 수 있다.
- **무결성 보장**: 모든 커밋은 SHA-1 해시로 식별되어, 파일이나 히스토리가 변조되면 즉시 감지할 수 있다.
- **비선형 개발 지원**: 여러 브랜치에서 동시에 작업하고 나중에 병합(merge)하는 방식의 개발이 가능하다.

### Git이 왜 필요한가

1. **변경 이력 관리**: "언제, 누가, 무엇을, 왜" 변경했는지 커밋 메시지와 함께 기록되므로 문제가 생겼을 때 원인 추적이 쉽다.
2. **협업 지원**: 여러 명이 같은 프로젝트를 동시에 작업해도 각자의 변경 사항을 브랜치로 분리했다가 병합할 수 있어 충돌을 최소화한다.
3. **백업 및 복구**: 실수로 코드를 삭제하거나 잘못 수정해도 이전 커밋으로 되돌릴 수 있다.
4. **실험적 개발 가능**: 새로운 기능을 메인 코드에 영향을 주지 않고 별도 브랜치에서 자유롭게 시도해볼 수 있다.
5. **코드 리뷰 및 품질 관리**: GitHub 등과 연동하면 Pull Request를 통해 다른 사람의 코드를 리뷰하고 병합 전에 품질을 검증할 수 있다.
6. **원격 협업**: GitHub, GitLab 같은 원격 저장소를 통해 지리적으로 떨어진 팀원들과도 코드를 공유하고 동기화(push/pull)할 수 있다.

### Git이 없다면?

- 파일을 `최종.py`, `최종_진짜.py`, `최종_진짜_수정.py` 처럼 수동으로 버전 관리해야 한다.
- 여러 명이 같은 파일을 수정하면 서로의 작업을 덮어쓸 위험이 크다.
- 특정 시점의 코드로 되돌리기 어렵고, 무엇이 왜 바뀌었는지 알기 힘들다.

## 브랜치 전략 비교

| 구분 | Git Flow | GitHub Flow | GitLab Flow | Trunk-Based Development |
|---|---|---|---|---|
| **핵심 개념** | 기능/릴리즈/핫픽스를 위한 다수의 정형화된 브랜치 체계 | 단일 `main` 브랜치 + 기능 브랜치의 단순한 흐름 | GitHub Flow에 환경별(스테이징/프로덕션) 브랜치 개념을 추가 | 모든 개발자가 하나의 브랜치(trunk/main)에 매우 자주 병합 |
| **주요 브랜치** | `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` | `main`, `feature/*` | `main`, `pre-production`, `production`, `feature/*` (또는 환경별 브랜치) | `main` (trunk) + 수명이 짧은 feature 브랜치 |
| **브랜치 생명주기** | 길다 (release, develop은 상시 유지) | 짧다 (기능 완료 후 바로 병합·삭제) | 중간 (환경 브랜치는 상시, feature는 짧게) | 매우 짧다 (하루~며칠 내 병합) |
| **릴리즈 방식** | 정해진 주기로 `release` 브랜치를 따서 QA 후 배포 | `main`에 병합되면 바로/지속적으로 배포 (CD 지향) | 환경 브랜치를 따라 순차적으로 배포 | `main`에서 언제든 배포 가능한 상태 유지, 배포는 별도 태그/플래그로 제어 |
| **병합 빈도** | 낮음 (기능 단위로 크게 병합) | 높음 | 중간~높음 | 매우 높음 (하루 여러 번) |
| **CI/CD 적합성** | 상대적으로 낮음 (브랜치가 오래 살아있어 통합 지연) | 높음 | 높음 | 매우 높음 (지속적 통합의 이상적 형태) |
| **충돌(Merge Conflict) 위험** | 브랜치 수명이 길어 충돌 위험 큼 | 낮음 (자주 병합) | 낮음~중간 | 매우 낮음 (항상 최신 상태 유지) |
| **학습 난이도** | 높음 (브랜치 종류와 규칙이 많음) | 낮음 (구조가 단순) | 중간 | 낮음 (구조는 단순하나 팀 규율 필요) |
| **장점** | 릴리즈/핫픽스 관리가 체계적, 대규모·정기 릴리즈에 적합 | 단순하고 이해하기 쉬움, 빠른 배포에 적합 | 환경별 배포 이력 관리가 명확함 | 통합 지연 없음, 충돌 최소화, CI/CD와 궁합이 좋음 |
| **단점** | 브랜치가 많아 복잡함, 병합 지연으로 충돌 발생 가능 | 버전 관리(릴리즈 태깅)가 약함, 여러 배포 환경 관리에 불리 | Git Flow보다는 단순하지만 여전히 규칙이 필요함 | 팀의 높은 규율과 강력한 테스트 자동화 필요, 기능 플래그 관리 부담 |
| **적합한 상황** | 정해진 일정으로 배포하는 대규모 소프트웨어, 여러 버전을 동시에 유지보수해야 하는 경우 | 웹 서비스 등 지속적 배포(CD)를 하는 소규모~중규모 팀 | 여러 배포 환경(스테이징/프로덕션)을 명확히 구분해야 하는 팀 | 빠른 반복과 지속적 배포를 지향하는 팀, 성숙한 테스트 문화를 가진 팀 |
| **대표 사용 예** | 데스크톱/모바일 앱, 정기 버전 출시 소프트웨어 | GitHub 자체, 다수의 오픈소스 웹 프로젝트 | GitLab, 다단계 배포 파이프라인을 쓰는 조직 | Google, Facebook 등 대규모 CI/CD 조직 |
